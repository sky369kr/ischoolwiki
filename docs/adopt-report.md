# /adopt 진단 보고서 (2026-11-13)

하네스 v4 이전에 만들어져 이미 운영 중인 사이트(https://ischoolwiki.sky-b9d.workers.dev, ischoolwiki.com 연결 배포 대기)를 하네스 구조로 편입하기 위한 진단. 코드는 고치지 않았다.

## 요약
- 사이트는 동작한다. 세 학교(BSB Shunyi, DAIS, BST Tashkent)에 영어 18편 + 한국어 번역이 자동 게시되어 있고, 검사 명령 `bash scripts/check.sh`는 전체 PASS.
- P0(지금 공개된 내부 문서, 커밋된 비밀 값)는 없다.
- 가장 큰 위험은 코드가 아니라 **자동 글의 품질**: 검사를 통과해도 사람이 읽으면 걸리는 문제(출처 오인용, 학생 실명, 목록 누락)가 이번 주에만 세 종류 나왔고, 매번 사람이 운영 사이트에서 발견했다. 자동 검사가 못 잡는 부분을 사람 점검(안정화 기간 일일 점검)이 메우고 있다.
- 기준 문서(PRD, 디자인 명세, 구조 설계, SEO 계획)가 없어서, 지금까지의 범위·결정은 README와 docs/decisions.md에 흩어져 있다. 이번 역기획으로 초안을 만든다.

## 1. 내부 문서 노출 — 이상 없음
- `bash scripts/verify-live.sh` (운영 workers.dev): 19개 내부 경로 전부 404, PASS.
- Worker는 코드에 정의된 라우트만 응답하고 `[assets]`·`[site]` 설정이 없다. 저장소의 .md(CLAUDE.md, README.md, start.md, tools/ai-measure/ 보고서)는 공개되지 않는다.
- `scripts/check.sh 40`이 로컬에서도 같은 내용을 매번 확인한다.

## 2. 비밀 값 — 이상 없음
- git 기록 전체를 패턴으로 검색: 걸린 줄은 검사 스크립트의 패턴 문자열과 `pilot.sh`가 환경 변수를 `.dev.vars`로 옮기는 코드뿐, 실제 키 없음. `.dev.vars`·`.env`가 커밋된 적 없음.
- 운영 사고: 2026-11-12~13에 관리 비밀번호(ADMIN_TOKEN)가 채팅에 세 번 노출됨. 매번 새로 발급해 교체함(사람 작업 완료). 안전한 입력 방법(`ADMIN_TOKEN=$(openssl rand -hex 32)` 후 등록)으로 정리.

## 3. 회원 보호 — 해당 없음 / 관리 경로 이상 없음
- 회원 기능 없음. 보호 대상은 `/admin/*` 4개 경로(run, import-ispp, unpublish, held): 토큰 없이 401(check 40). 토큰 비교는 해시 후 상수 시간 비교.

## 4. D1 — 양호
- 스키마는 `migrations/0001`~`0006` 파일로만 관리. 원격 적용 기록 일치(0006까지, 사람이 적용).
- 쿼리는 모두 `prepare + bind`. 문자열로 SQL을 잇는 곳 두 곳(`src/index.ts` `published()`의 `sql` 조각, `src/pipeline.ts` `unpublish()`의 `where`)은 코드 상수만 이어 붙이고 값은 bind라 주입 위험은 없으나, 규칙(16장) 문구와는 어긋남 → 구조 정리 후보.

## 9. SEO 기본
- 공개 페이지마다 title·description·h1 1개·lang·canonical(SITE_URL=ischoolwiki.com 기준)·hreflang(글), Schema.org(BlogPosting, FAQPage, BreadcrumbList, EducationalOrganization, ItemList, WebSite), sitemap.xml·rss.xml·llms.txt·robots.txt(AI 크롤러 허용) 있음. check 20 PASS.
- 도메인 연결 전이라 canonical이 아직 열리지 않는 주소를 가리킴 → 배포 후 해소. workers.dev 주소는 canonical로 정리됨(별도 리디렉트 없음).
- 한국어 학교·비교 페이지가 없어 한국어 글의 hreflang 짝은 글 페이지에만 있음.

## 가장 위험한 문제 5개
1. **자동 글의 사람 눈 품질** (P1 성격): 검사 통과 후에도 출처 표현 부정확(메뉴 목록), 표현상 과장 위험. 대응: 안정화 기간 일일 점검(예약 작업), 문제 유형이 나오면 작성 지시·검증기에 반영.
2. **글 교체 절차가 사람 손 3단계**(내리기 → 원격 DB에서 소식 되돌리기 → 실행): 이번 주에 4번 했고 한 번은 실수로 중간 단계만 실행됨. 관리 API 하나로 묶을 후보.
3. **관리 비밀번호 취급**: 채팅 노출 3회. 절차 문서화(runbook) 필요.
4. **구조 집중**: `src/index.ts`, `src/pipeline.ts`에 기능이 몰려 있어 수정 회귀 위험. 테스트는 검증기 중심이고 페이지·파이프라인 흐름 테스트는 얕음.
5. **기준 문서 부재**: PRD·구조 설계가 없어 "무엇이 v1 범위인가"가 결정 기록에만 있음 → 이번 역기획으로 해소.
